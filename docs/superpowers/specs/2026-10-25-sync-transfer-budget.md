# 변경분 동기화 전송량 최적화

사용자가 승인한 10월 25일 진단의 첫 조치다. 전체 자료·표지·목차·수정 이력의 기기 저장 범위, 계정 분리, 미전송 입력, 충돌 처리와 기존 이어받기 커서를 보존한다. 운영 DB의 한도는 소진되어 있으므로 개인 DB 접근·초기화·실기기 동기화 검수는 하지 않는다. 실제 PC/iPhone 검수는 11월 1일에 진행한다.

## 선택한 방식

기존 readSyncChanges는 이벤트 최대 200건의 값을 DB에서 받은 다음에 512 KiB 응답 제한을 적용한다. DB 안에서 이벤트 순서와 용량을 함께 계산하고, 실제 내보낼 값만 받도록 바꾼다. 사용자 요청의 ‘우선 동기화 최적화’에 따라 진단의 이 조치를 직접 구현한다.

- 선택: 이벤트 페이지의 키를 먼저 중복 제거하고 현재 값을 DB 안에서 구성한다. 처음 등장한 이벤트 순서로 용량 한도를 적용하며, 제외된 첫 이벤트 직전까지만 커서를 전진한다. 같은 페이지 안의 반복 변경은 현재 값 한 건으로 합친다.
- 제외: 단순 limit 축소는 자료 크기에 따라 다시 낭비하거나 요청을 과다하게 만든다. 최신 행 순서로 커서 의미를 바꾸는 방식은 기존 기기의 이벤트 커서와 복구 규칙에 불필요한 영향을 준다.
- 기존 전체 scan은 이미 DB 안에서 용량을 제한하므로 그대로 유지하고, 행 기술 정보의 SQL 표현을 공유해 해시·조각 형식의 일관성을 유지한다.

## 보장할 동작

- DB에서 반환하는 변경 자료 합계와 기기로 보내는 한 페이지가 각각 512 KiB 이하이며, 잘린 값이 매번 DB에서 재전송되지 않는다. 메타데이터/커서 여유 공간 16 KiB를 유지한다.
- 이벤트의 수치 순서와 기존 limit 의미를 유지하고, 처리하지 않은 키를 건너뛰지 않는다. 삭제·복원, 여러 테이블, 키 없는 단일 행, 한도보다 큰 원본의 조각 전송을 보존한다.
- 첫 누락된 자료는 409로 처리하고, 변화가 없으면 값을 조회하지 않는다. 계정 비밀정보 제거와 읽기 전용 역할에서 동작한다.
- 변경 없는 확인, 메모 하나 변경, 중단 후 재개 및 미전송 입력 보존을 생성 자료로 검증한다. 측정치는 JSON 결과 바이트이며 Neon 청구 바이트와 동일하다고 표현하지 않는다.
- DB 변경, 앱 프로토콜 버전 변경, 전체 재다운로드 및 새 의존성은 필요 없다.

표지의 온라인 캐시와 백업 전송량 개선은 별도 조치이며, 이번 변경은 동기화 경로에 집중한다.
