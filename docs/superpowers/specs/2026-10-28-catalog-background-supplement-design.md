# ISBN-based background catalog supplementation

The user approved fast Yes24 registration followed by ISBN-based library supplementation, and authorized resolving the existing catalog review queue with covers favored. Save operations enqueue work in the existing book enrichment JSON inside the same transaction; no provider request blocks saving. A PC collector with its existing private API credentials polls only pending books in bounded batches, caches provider responses by ISBN, retries temporary failures, and writes owner-locked, version-checked changes through the existing sync path. The public server never receives the library key.

Yes24 supplies introductions, contents and covers; the library supplies missing facts, fallback covers and verified KDC classification. Both are queried for an identified ISBN, even when Yes24 has results. Papers, periodicals and excluded books remain outside collection. Missing ISBNs are not inferred from a search hit alone. Human fields, covers and reviewed/hidden curation remain protected. Provider evidence is retained internally.

Review cleanup works per owned book, never merging separate copies with the same ISBN. Valid matching ISBN plus compatible title and no conflicting populated author/publisher permits filling missing facts and supplementing contents/covers; conflicting editions remain pending. Choose matching candidates with usable covers and contents first. Store image bytes before accepting cover supplementation. Old alternatives are superseded with an audit record, not physically deleted. A rerun is idempotent. Preserve personal notes and reading history and verify their fingerprints before/after the live run.

Approaches considered: requesting both services during search would slow the interface; a durable PC queue preserves the registered-IP library credential and existing deployment. Queue state uses the existing enrichment JSON rather than a new database table, and the PC checks only pending entries, with no whole-library polling.
