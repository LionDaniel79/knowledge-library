# 지식서재 전체 데이터 기기 저장과 변경분 동기화 설계

상태: 사용자 검토용 설계. 운영 앱과 DB에는 아직 적용하지 않았다.

## 목표와 확정된 범위

PC와 아이폰 각각에 본인 계정의 온라인 지식서재 자료 전체를 보관한다. 처음 한 번 전체를 내려받은 뒤 화면 조회·정렬·검색은 기기 저장소에서 처리하고, 추가·수정·삭제·제외·복원만 서버와 동기화한다. 자주 보는 자료만 남기는 캐시나 표지 용량 제한 방식으로 대체하지 않는다.

포함 범위는 소장 도서 전체, 제외한 자료, PDF 파일의 온라인 등록 정보, 서지·표지 이미지·목차·소개, 원본 가져오기 데이터, 메모와 휴지통, 독서 이력, 수정 이력, 책장·태그·분류, 검토 후보와 출처, 사유의 지도·연결·생각 변화, 연구 자료, 저장된 AI 요청·결과·비용·설정이다. 출처와 세부 이력은 기존 화면처럼 필요할 때 펼치되 기기에는 모두 저장한다.

외장하드의 PDF 원본·본문 색인·OCR 중간파일은 복제하지 않는다. 이미 온라인 DB에 있는 PDF 등록 정보와 저장된 인용·메모는 복제한다. 계정 비밀번호·로그인 세션·접근 토큰·API 비밀키·서버 실행 자격증명과 다른 계정의 자료는 동기화 대상이 아니다. 기기·연결·처리 상태는 사용자에게 표시하는 안전한 필드만 복제하며 실행 권한은 서버가 검증한다.

온라인 DB는 공통 확정본과 기기 간 동기화를 유지한다. 기기 사본을 만들어도 기존 온라인 원본은 삭제하지 않는다. 도서 5,208건의 제외 상태와 보류 37건, 복원 기능을 유지한다.

## 현재 코드와 실제 데이터

- 목록은 현재 서버에서 페이지별로 받으며 전체 DB를 매번 받지는 않는다. `use-paged-resource.ts`와 `use-book-catalog.ts`는 조건 변경마다 `no-store` 요청을 수행한다.
- `library-app.tsx`는 저장 뒤 `/api/library`를 다시 읽는다. 도서·메모 상세도 별도 요청한다.
- `app/page.tsx`는 인증과 DB의 `overview()`가 끝나야 서재 화면을 반환한다. 브라우저 저장소만 추가하면 첫 화면의 이 대기는 남는다.
- 현재 서비스 워커는 공개 오프라인 메모 화면만 저장한다. 전체 서재를 오프라인에서 열거나 전체 자료를 기기에 보관하는 구조는 없다.
- 기존 UUID·수정 버전·요청 ID·`library_operations` 중복 처리 방지와 오프라인 임시 기록을 재사용한다. 수정 시간이 없는 테이블과 직접 SQL로 갱신하는 수집 프로그램도 있어 수정 날짜만 비교하는 방식은 부적합하다.

2026-10-17 읽기 전용 측정에서, 본인 계정의 38개 앱 자료 테이블 160,281행을 비밀 필드 없이 JSON으로 표현한 크기는 **232,636,353바이트, 약 221.86MiB**였다. 인증 테이블과 서버 전용 실행 정보는 측정에서 제외했다. 표지는 이 수치에서 base64로 계산됐다.

| 큰 데이터 묶음 | 행 수 | JSON 바이트 |
| --- | ---: | ---: |
| 수정 이력 | 56,752 | 66,620,399 |
| 도서정보 검토 | 15,196 | 42,005,842 |
| 표지 이미지 | 3,285 | 37,444,740 |
| 자료 정리 항목 | 8,895 | 18,008,130 |
| 도서 전체 | 10,994 | 15,238,593 |
| 필드별 출처 | 9,009 | 14,832,448 |

이는 다운로드 시간이나 실제 저장 용량 보장이 아니다. 로컬 색인·진행 중인 전송·기존 세대 보존에 추가 공간이 필요하다. 초기 공간 검사는 실측 데이터 크기를 기준으로 하고, 검수용 여유 공간은 기기당 약 1GiB를 출발점으로 삼되 구현 후 실제 최고 사용량으로 조정한다. 공간이 부족하면 미완료로 표시하고 재개한다. 사용자가 요청한 전체 자료를 몰래 일부만 남기지 않는다.

## 접근 방식과 선택

| 방식 | 전체 저장 | 장점 | 비용과 제약 |
| --- | --- | --- | --- |
| 기존 웹앱을 PWA로 확장하고 IndexedDB에 전체 저장 | 가능 | PC·아이폰에 같은 코드 사용, 별도 앱스토어 배포 불필요 | 저장 위치는 브라우저가 관리하며 저장 공간 정책의 영향을 받음 |
| PC·아이폰 전용 앱과 SQLite | 가능 | 앱 전용 DB 파일 관리가 명확함 | 두 플랫폼의 설치·업데이트·배포 작업이 추가됨 |

첫 구현은 **전체 저장 PWA + IndexedDB + 기존 Neon DB의 변경 기록**으로 한다. 동기화 프로토콜을 저장 엔진과 분리해 추후 네이티브 SQLite 앱에서도 재사용할 수 있게 한다. 별도 유료 동기화 서비스나 AI는 필요 없다. 기존 DB·웹 호스팅 사용량은 초기 전체 전송과 변경 기록 보관만큼 늘 수 있다.

PC의 IndexedDB는 브라우저 프로필 안의 앱 전용 저장소이며 사용자가 탐색기에서 임의의 D/E 폴더를 지정하는 방식은 아니다. 아이폰도 홈 화면에 추가한 웹앱의 저장소를 사용한다. PC에서 특정 드라이브의 DB 파일을 직접 지정하는 요구가 추가되면 PC용 SQLite 저장 어댑터를 별도로 연결한다. 큰 외장 파일을 C드라이브로 복사하지 않는다.

## 기기 저장 구조

하나의 로그인 계정마다 독립된 복제 공간을 사용한다. 다음 영역을 IndexedDB의 별도 object store 또는 명확한 레코드 유형으로 분리한다.

1. **전체 업무 자료:** 위 포함 범위의 모든 레코드. 서버 자료와 로컬 변경 중인 값을 분리한다.
2. **이미지와 큰 값:** 표지의 실제 이미지 바이트, 큰 가져오기 JSON 등을 해시로 식별한 조각으로 저장한다. 모든 이미지·큰 값이 내려와야 전체 저장 완료로 판단한다. 임의의 LRU 삭제나 썸네일만 보관하는 방식은 사용하지 않는다.
3. **검색·정렬용 색인:** 제목·저자·ISBN·태그·분류·책장·날짜·본문 텍스트에서 다시 만들 수 있는 파생 데이터. Web Worker에서 만들고 조회한다.
4. **보낼 변경 목록:** 명령 ID, 대상 ID, 기준 서버 버전, 입력 값, 생성 순서, 재시도 상태를 저장한다.
5. **동기화 상태:** 서버의 마지막 적용 순번, 데이터 세대, 최초 다운로드의 테이블·페이지·조각 진행률, 해시와 저장 공간 상태.
6. **충돌 기록:** 기기의 입력, 기준 자료, 최신 서버 자료와 선택 결과. 해결 전에도 원문을 유지한다.

표지와 목차를 화면에 한꺼번에 렌더링하거나 222MiB 전체를 메모리에 올리지 않는다. 각 화면은 기기 DB에서 필요한 행만 읽고 기존 10·15·30·50개 페이지 설정을 유지한다. 저장 범위와 화면 표시량을 구분한다.

대표 앱 주소는 기존 공개 서재 주소로 유지한다. 공개 주소와 비공개 PC 주소는 웹 저장소가 서로 분리되므로 같은 저장소를 공유한다고 가정하지 않는다. 전체 자료 저장과 일반 서재 사용은 대표 앱 주소에 모으고, PC 연결 주소는 PDF 원문·로컬 작업 상태 접근에 사용한다. 기존 PC 링크의 동작은 호환성을 보존하면서 안내와 이동을 정리한다.

## 서버 DB 변경과 변경분 다운로드

기존 업무 테이블을 새 DB로 옮기지 않는다. 다음 동기화 전용 구조를 추가한다.

- `library_sync_heads`: 계정별 확정 순번과 스키마 세대.
- `library_sync_changes`: 계정·순번·자료 유형·기본키·추가/수정/삭제 알림. 삭제된 행도 알 수 있게 한다.
- `library_sync_row_versions`: 각 자료의 마지막 변경 순번과 삭제 상태. 최신 값 조회·중복 적용 방지에 사용한다.
- `library_sync_devices`: 기기 ID, 마지막 확인 순번·동기화 시간·프로토콜 버전. 비밀키는 복제하지 않는다.

인증된 API가 허용된 자료 유형과 필드만 내려준다. 클라이언트가 테이블 이름이나 SQL을 보내도록 하지 않는다. 계정 ID는 검증한 로그인 세션에서 정한다.

변경 기록은 원본 자료를 쓰는 **같은 트랜잭션**에서 DB 트리거로 작성한다. 웹 수정뿐 아니라 도서정보 수집, 가져오기, 표지 저장, 일괄 제외와 복원, 백업 복원도 빠짐없이 포착한다. 잘못된 트리거 때문에 삭제·복원이 누락되거나 사용자 입력만 동기화되는 구조를 금지한다.

계정별 헤드 행 잠금으로 쓰기 순서를 직렬화한다. 앱·수집기·가져오기·복원 등 공통 쓰기 진입점에서 업무 행을 잠그기 전에 계정 잠금을 먼저 획득하고, DB 트리거는 변경 추적 누락을 방지한다. 잠금 획득 순서와 거래 재시도를 검사한다. 단순 `bigserial` 최댓값을 커서로 쓰면 늦게 커밋한 거래를 건너뛸 수 있으므로 그렇게 구현하지 않는다. 롤백한 거래의 자료는 확정 순번에 포함되지 않는다.

변경 API는 짧은 읽기 전용 일관성 트랜잭션에서 변경 키·현재 값·각 행의 순번·서버 헤드를 함께 읽는다. 현재 행 값이 변경 알림보다 최신이면 그 실제 순번을 함께 전달한다. 기기는 더 오래된 값을 덮어쓰지 않으며 커서는 실제 처리한 변경 알림까지만 전진시킨다. 같은 레코드가 다음 응답에 반복돼도 무해해야 한다.

자료 변경이 없으면 작은 헤드/상태 응답만 반환한다. 표지의 해시가 그대로면 이미지 바이트를 다시 보내지 않는다. 삭제·휴지통·제외·복원은 서로 구분해 복제한다.

변경 알림 보존 기간의 기본값은 180일이다. 기기의 커서가 보존 범위를 벗어나면 전체 재구성을 요청하되 기기의 미전송 입력을 유지한다. 업무 자료의 수정 이력과 도서 제외 상태는 이 알림 보존 기간 때문에 삭제하지 않는다.

## 최초 전체 내려받기

1. 인증한 계정과 스키마 세대를 확인하고 저장 가능 공간을 점검한다.
2. 변경 추적이 적용된 시점 이후의 시작 커서를 확보한다.
3. 모든 허용 테이블을 기본키 순서로 나누어 로컬 준비 세대에 저장한다. 기존 세대와 미전송 입력을 먼저 지우지 않는다.
4. 큰 레코드와 이미지도 제한 크기의 조각으로 내려받고 해시를 검사한다. 최대 응답 크기를 제한해 Vercel 요청 한도와 아이폰 메모리 사용을 피한다. 가져오기 JSON 한 행이 수 MiB여도 한 응답에 넣지 않는다.
5. 전체 스캔 동안 생긴 추가·수정·삭제를 시작 커서 이후의 변경 기록으로 따라잡는다. 스캔 중 기본키 뒤쪽에 삽입되거나 앞쪽에서 삭제된 행도 이 과정으로 복구한다.
6. 모든 테이블과 큰 값의 전송 완료, 행 수·자료 해시와 변경 반영 상태를 검증한 후 활성 세대를 원자적으로 전환한다.

여러 HTTP 요청 동안 DB 트랜잭션을 길게 열어 두거나 서버 메모리에 전체 자료를 묶어 놓지 않는다. 최초 스캔과 변경분 따라잡기로 일관성을 확보한다. 전송 중 중단되면 마지막 검증 완료 조각부터 재개한다.

처음 전체 저장을 마치기 전에는 기존 온라인 화면을 사용할 수 있지만 ‘전체 저장 완료’로 표시하지 않는다. 이미지·이력 등이 덜 받아졌으면 그 개수와 남은 용량을 보여준다. 최초 다운로드는 필요한 모든 자료를 실제로 전송하는 작업이며 다운로드 비용과 시간은 실측한다.

## 기기에서 수정하고 업로드하기

일반 작성·수정은 로컬 DB에 변경 목록과 함께 한 거래로 저장한다. 로컬 저장이 성공해야 ‘기기에 저장됨’을 표시한다. 서버 확인 전에는 ‘동기화 완료’로 표시하지 않는다.

- 온라인이면 저장 후 변경분을 보낸다. 오프라인이면 보낼 목록에 보존한다.
- 기존 요청 ID 기반 중복 방지와 버전 검사를 유지한다. 서버가 처리한 응답을 기기가 못 받았어도 같은 요청 ID로 재시도한다.
- 여러 오프라인 편집을 같은 레코드에 했으면 그 의존 순서를 보존한다. 서버 확인 전의 후속 입력을 첫 응답으로 덮어쓰지 않는다.
- 새 도서·메모 등의 로컬 UUID를 서버 명령에서 검증해 수용하는 경로를 추가한다. 기존 클라이언트 명령과 호환되게 하고 충돌 시 다른 자료를 덮어쓰지 않는다.
- 일반 도서·메모·독서 상태·태그·책장·사유의 지도 판단과 제외 자료 복원은 로컬 변경 목록을 지원한다.
- 인터넷 서지 검색·GPT 요청·실제 PDF 접근 등 외부 자원이 필요한 기능은 연결 상태를 표시한다. 오프라인에서 쌓인 항목 때문에 AI 유료 호출을 자동 실행하지 않는다.
- 영구 삭제·대용량 가져오기·연결 권한 변경은 기존 확인·권한 검사를 유지하고 온라인에서 확정한다. 해당 기능을 위해 자료 전체를 다시 내려받지는 않는다.

서버가 거절한 변경은 원문을 보존하고 해당 입력에 이유를 표시한다. 성공하지 않은 입력을 보낼 목록에서 지우지 않는다.

## 두 기기의 수정 충돌

사용자가 작성한 글에는 마지막 저장 시각만 보고 한쪽을 덮어쓰는 방식을 사용하지 않는다. 기준 버전과 최신 버전이 다르면 입력·기준·서버 최신본을 비교해 선택하거나 합친다. 해결본도 새 버전 검사와 수정 이력으로 확정한다.

다른 자료를 각각 수정한 경우에는 독립적으로 동기화한다. 삭제된 메모의 오프라인 수정, 제외/복원과 도서 수정이 겹친 경우도 충돌 대상으로 보존한다. 자료 전체 복제는 같은 로그인 계정끼리만 이루어지고 계정 전환으로 다른 계정의 자료를 노출하지 않는다.

## 시작 속도와 동기화 시점

동기화가 끝난 기기는 첫 화면부터 기기 DB를 읽는다. 현재 `app/page.tsx`의 서버 DB 조회 완료를 기다리는 진입 구조를 클라이언트 셸로 분리한다. 서비스 워커는 버전이 있는 앱 코드·CSS·아이콘을 저장하고, 인증 HTML·로그인 토큰·일반 API 응답 전체를 공용 캐시에 넣지 않는다. 개인 데이터는 계정별 IndexedDB에서 다룬다.

동기화는 앱 시작·화면 복귀·인터넷 재연결·저장·수동 동기화 때 수행한다. 변경이 없을 때 불필요한 빈번한 폴링을 피하고, 열린 화면에서는 짧은 변경 알림 또는 적응형 확인으로 다른 기기의 수정을 반영한다. 한 기기의 여러 탭은 리더 조정으로 중복 전송을 줄인다.

아이폰에서 앱을 닫은 상태의 계속 실행을 필수 조건으로 삼지 않는다. 복귀하면 밀린 변경만 이어서 처리하며 지원되는 환경에서만 백그라운드 동기화를 보조적으로 쓴다.

## 저장 공간과 자료 보존

`navigator.storage.estimate()`로 공간을 확인하고 `persist()`를 요청하며 실제 허용 여부를 표시한다. 홈 화면에 추가한 아이폰 웹앱 사용을 안내한다. 저장 권한 요청이 언제나 승인되거나 브라우저 저장소가 영구 보장된다고 설명하지 않는다.

공간 부족·사이트 데이터 삭제·앱 제거 후에는 온라인 확정본에서 전체를 복구할 수 있다. 다만 아직 전송하지 않은 입력은 서버에 없으므로 동기화 대기 표시와 로컬 입력 내보내기를 제공한다. ‘이 기기의 자료 지우기’는 전체 자료 중 미전송 입력을 먼저 확인하고 저장·내보내기 절차를 거친다.

전체 저장 모드에서는 용량을 줄이기 위해 표지·과거 기록을 자동 삭제하지 않는다. 자동 정리할 수 있는 것은 성공적으로 전달된 전송 조각과 다시 만들 수 있는 검색 색인뿐이다. 전체 저장이 불가능하면 사용자가 알 수 있게 중단·재개하거나 네이티브 앱 경로로 전환한다.

## 사용자가 보는 화면

‘나의 서재’ 상단 ‘책 추가’ 버튼 왼쪽에 ‘동기화’ 버튼을 둔다. 사용자의 2026-10-17 추가 요청이며, 실제 변경분 동기화와 진행/결과 상태를 연결한다.

기기 저장·동기화 설정에 다음 정보를 간결하게 표시한다.

- 전체 저장 중/완료, 내려받은 자료 수와 바이트, 남은 이미지·큰 자료.
- 마지막 동기화 시간, 기기에 저장한 총량과 여유 공간.
- 동기화 대기·실패·충돌 수와 ‘지금 동기화’.
- ‘입력 내보내기’, ‘이 기기 다시 구성’, ‘이 기기의 자료 지우기’.

목록을 바꿀 때 빈 화면과 서버 로딩 문구를 먼저 보이지 않는다. 동기화 중에도 이미 저장된 자료를 읽는다. ‘기기에 저장됨’, ‘동기화 대기’, ‘동기화 완료’를 구분한다. 세부 동기화 기록은 사용법/상세 상태에서만 펼친다.

## 구현 순서와 검수 기준

1. 전체 자료·보안 필드 목록과 저장 어댑터, 변경 추적 스키마를 확정한다. 운영 복제 DB에서 마이그레이션·모든 쓰기 경로를 검사한다.
2. DB의 변경 추적과 인증된 전체 내려받기/변경분 API를 만든다. 기존 앱은 계속 사용할 수 있게 한다.
3. 전체 저장·분할 전송·해시 검사·재개·세대 전환과 이미지 저장을 구현한다.
4. 앱 진입과 도서·메모·검색·달력·통계·이력·검토·사유의 지도 조회를 기기 저장소로 옮긴다.
5. 로컬 작성·보낼 목록·충돌 해결·여러 탭 조정과 기존 임시 기록의 안전한 이전을 구현한다.
6. 서비스 워커 업데이트, 공간 관리, 기기별 실제 검수 후 웹/PC 연결 화면에 순차 배포한다.

필수 검사:

- 모든 허용 업무 테이블의 행 수·키·내용 해시와 이미지 해시가 서버와 기기에서 일치한다. 제외 자료·원본 가져오기 데이터·과거 이력을 검사에 포함한다.
- 온라인 DB를 읽지 않고 저장된 전체 목록·상세·표지·목차·메모·이력·검색·달력·통계를 연다.
- 변경이 없을 때 전체 자료/목록/이미지를 다시 보내지 않는다. 메모 한 건 수정 시 관련 변경과 그로 생긴 이력만 전달한다.
- 두 PC/iPhone의 왕복 동기화, 오프라인 수정 충돌, 요청 응답 유실, 중복 재시도, 삭제 후 재접속, 제외와 복원, 재색인을 검증한다.
- 늦게 커밋한 변경, 스캔 중 삽입·수정·삭제, 180일 지난 기기, 전체 다운로드 중 중단·업데이트·공간 부족을 검증한다.
- 계정 전환·로그아웃·만료 세션·변조된 커서·다른 계정 기기 ID로 자료가 섞이지 않는다.
- 예전 오프라인 임시 기록을 손실 없이 옮기며 미전송 입력이 있는 상태에서 재구성해도 입력을 보존한다.
- 로컬 준비가 끝난 PC의 목록·정렬 응답 p95 200ms, 아이폰 p95 400ms를 목표로 측정한다. 목표 달성 여부는 실제 기기에서 확인하며 지금 보장하지 않는다.

- [WebKit 저장 정책과 Storage API](https://webkit.org/blog/14403/updates-to-storage-policy/): 기기 저장, 저장 공간 추정, 영속 저장 요청, 홈 화면 웹앱과 자동 제거 조건.
- [MDN 저장 용량과 제거 기준](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria): IndexedDB/Cache/OPFS와 origin별 저장 영역.
- [MDN Background Synchronization API](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API): 백그라운드 동기화는 지원 범위가 제한된 보조 수단.

자료 크기는 운영 DB의 읽기 전용 합계로 측정했다. 현재 느림의 원인을 네트워크 하나로 확정한 성능 측정은 아니며, 구현 전후 같은 기기·같은 작업의 전송량과 표시 시간을 비교한다.
