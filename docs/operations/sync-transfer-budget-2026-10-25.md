# 동기화 DB 반환량 최적화 (2026-10-25)

## 변경

변경분 조회는 최대 200개의 이벤트에서 중복 키를 DB 안에서 합치고, 첫 이벤트 순서에 따라 512 KiB 응답 예산을 적용한다. 내보내지 않을 큰 값을 서버로 먼저 가져오지 않는다. 다음 페이지로 밀린 키의 첫 이벤트 이전까지만 커서를 전진하며, 최신 값의 revision으로 커서를 뛰어넘지 않는다.

행 표현은 초기 scan과 공유하므로 기존 해시·조각·비밀정보 제거 형식은 유지된다. DB 스키마, 기기 저장소, 전체 저장 범위, SYNC_PROTOCOL=1, 미전송 입력 및 충돌 정책은 바꾸지 않았다. 초기 전체 scan은 원래 DB 내부에서 제한하므로 변경분과 같은 문제로 취급하지 않는다.

## 검증

- 생성 도서 200건: DB 결과 JSON 합계 **102,406,513 → 9,950,365 bytes (90.28% 감소)**. 수정 후 20페이지에서 200건 모두 전달, 실제 내용 합계 9,675,892 bytes.
- 수정 전에는 첫 페이지를 위해 DB에서 9,732,185 bytes를 받아 앱에서 잘랐다. 수정 후 각 DB 결과와 기기 응답은 512 KiB 이내다.
- 기기 저장 완료 후 변경 없음: DB 결과 JSON 156 bytes. 메모 한 건을 생성·수정한 뒤 최신 값 수신: 1,017 bytes. 응답 유실 후 재개와 미전송 메모 유지 확인.
- A/B/A/C 중복 및 경계, 혼합 테이블, 삭제·복원, bigint 순서, 큰 값의 조각 해시, 누락 자료 409, 계정 경계, 읽기 전용 역할을 확인했다.
- 동기화·복제 관련 35파일 129검사 통과. 전체 Vitest 167파일 562검사 통과(기존 보류 2파일/4검사). 타입·변경 파일 포맷·diff 검사 통과.
- 신선한 전체 코드 검토 1회: 중요한 결함 없음. 검토자도 핵심 18검사를 독립 실행해 통과.
- Next 16.4.2 배포 빌드와 산출물 검사 통과: 추적 항목 18,056, 개인 자료 포함 0.

위 수치는 고립된 PGlite 생성 자료의 DB 결과 JSON이며 실제 Neon 청구 전송량과 같지 않다. 90.28%는 이 재현 조건의 개선 폭으로, 월 전체 트래픽 감소율을 보장하지 않는다. 사용자 자료·운영 DB·실기기 동기화를 호출하지 않았다.

기존 테스트의 테이블 수 38은 이미 추가된 화이트보드를 반영해 39로 고쳤다. 정확한 테이블·컬럼 대조는 유지한다. 보존 기간 검사는 중복 tombstone 수 대신 세 개의 고유 자료·삭제 키·최종 커서를 검증한다.

## 운영 환경

통합된 E: exFAT 볼륨에서 Node 24.21의 readlink가 일반 파일/디렉터리에 EISDIR를 반환해 webpack이 실패했다. 이번 로컬 빌드에만 lstat로 비링크임을 확인한 경우 표준 EINVAL로 정규화하는 사전 로딩을 사용했다. 저장소 소스·의존성 및 PC 실행 설정에 이 보정은 추가하지 않았고 배포 산출물에도 포함되지 않았다. 웹 Linux 빌드는 별도로 확인한다.

표지 온라인 캐시·전체 백업 최적화는 이 동기화 수정에 포함하지 않는다. 최초 전체 기기 저장량은 그대로이며 기존 저장본을 지우거나 처음부터 재수신하도록 요구하지 않는다.

실제 PC/iPhone 왕복과 청구량 측정은 사용자 지시대로 11월 1일 검수 목록에 유지한다. 다음 절차에서 새 전체 수신을 유발하지 않고 이어받기·변경 없음·메모 1개·표지 재열람을 측정한다.
