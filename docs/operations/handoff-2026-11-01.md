## 구현한 내용

1. PDF 원문검색: 일반 단어는 같은 페이지 안에서 AND 검색, 큰따옴표 안은 띄어쓰기를 포함한 어구 검색. ASCII 및 한국어 곡선 따옴표(방향이 뒤집힌 경우 포함)를 지원한다. 구문 오류와 기존 길이 제한을 명확히 검증한다. SQLite FTS 후보를 실제 페이지 텍스트로 재검증한 뒤 최대 40건을 반환한다.
2. 검색 결과: 일치하는 부분을 굵게 표시한다. 원문을 HTML로 해석하지 않으며 저장하는 인용문 자체는 바꾸지 않는다.
3. PDF로 PC 서재에 들어올 때 전체 기기 저장이 자동으로 시작되는 경로를 분리했다. 확인된 비공개 PC 주소의 PDF 진입에서만 시작·포커스·온라인 복귀·주기 조회의 자동 동기화를 보류한다. 일반 서재 메뉴로 이동하거나 수동 동기화를 누르면 기존 동기화가 진행된다. 사용자 저장 명령의 동기화는 유지한다.
4. 화이트보드: 생각묶음은 기본적으로 숨기고 연결관리에서 선택한 경우 표시한다. 기존 글감에 저장한 상자는 유지한다. 전체선택을 다시 누르면 모두 해제하며, 표시만 바꾸는 동작은 원본을 복제하거나 저장하지 않는다.
5. 생각묶음 삭제: 연결관리 목록의 삭제와 일반 화이트보드의 상자 삭제, 메모상자 상세 삭제는 동일한 `archiveMemoBundle` 명령을 사용한다. 개별 메모는 보존하고 연결된 생각묶음 관계는 해제한다. 소유자·버전·중복 요청 검사 및 오프라인 처리도 유지한다. 글감 보드에서의 상자 삭제는 그 글감의 목차 참조만 제거하는 기존 동작이다.
6. 삭제 직전 수정이 진행 중이면 먼저 기기 저장을 마친 뒤 확인된 최신 버전으로 삭제한다. 오래된 보드 참조나 이전 상자 정리 과정이 삭제된 원본을 다시 만들지 않도록 회귀 검사를 추가했다.

## 대량 동기화 조사 결과

- 원문검색 GET은 읽기 전용이며 저장 명령을 발생시키지 않는다. `/api/pdf/citation` POST는 실제 하이라이트 메모를 생성하므로 저장 후 동기화가 필요하다.
- 조회 당시 온라인 서재 업무 자료는 41개 테이블 계열, 합계 약 173,750건이었다. 주요 항목은 수정 이력 59,285건, 주제 연결 26,211건, 서지 후보 15,196건 등이다. 원본 PDF와 로컬 OCR 색인은 포함하지 않는다. 수치는 조사 시점의 참고값이다.
- 웹 주소와 PC 주소는 브라우저에서 서로 다른 저장 영역이다. PDF 검색 후 PC 주소로 이동하면 초기/중단된 전체 저장이 시작될 수 있었다. 이 경로에서 자동 시작을 보류했다.
- 당시 사용자의 실제 브라우저 체크포인트는 확보하지 못했다. 표시된 17만 건이 전부 신규 전송됐는지, 저장된 총건수가 표시된 것인지는 확정하지 않는다. 기존 자료나 전송 대기열은 초기화하지 않았다.

## 아직 확인하지 않은 항목과 다음 작업

- 실제 아이폰·아이패드에서 새 코드의 PDF 진입/메뉴 이동과 선택·삭제를 검수하지 않았다. Chromium 자동 검사와 실제 iOS 기기 검수를 구분해야 한다.
- 실제 17만 건 전체 재다운로드, 장시간 네트워크 단절 및 두 실기기의 동시 삭제/수정을 새로 실행하지 않았다. 가상 DB·기기 저장소와 기존 회귀 검사로 검증한다.
- 실제 외장하드 전체 OCR 색인에서 검색 품질·대규모 성능 측정은 수행하지 않았다. 이번 검색 검사는 SQLite 표본과 별도 검색 프로세스를 사용한다.
- 이번 작업용 DB 마이그레이션과 신규 인증키는 필요 없다. 기존 비공개 설정은 GitHub에 포함하지 않는다. 새 환경에서는 기존 운영 문서에 따라 환경변수를 별도로 연결해야 한다.
- 사용자의 최신 요청은 코드 안정화와 push이다. 이번 수정의 PC 운영 서버 교체·수동 웹 배포는 진행하지 않는다. GitHub push에 연결된 자동 배포 여부/결과는 별도 확인이 필요하다.
- 진행 중인 OCR·서지 수집기는 종료·재시작하지 않았다. 원본 PDF와 사용자 자료도 삭제하지 않았다.
- 다음 환경의 AI API 최적화는 이 커밋을 기준으로 별도 작업한다. 모델·프롬프트·전송 범위·비용 관련 동작은 이번에 변경하지 않았다.
