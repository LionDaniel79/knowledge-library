## 동기화 원인과 복구

`revision::text AS revision ORDER BY revision`은 숫자 변경 순번을 사전순으로 읽어 1000이 999보다 먼저 처리되고 중간 변경을 건너뛰었다. 숫자 컬럼 `c.revision`으로 정렬한다. 기존 기기는 `changeOrderVersion`이 없으면 원본 전체 재다운로드 대신 변경 이력을 재대조한다. 값 1은 복구 진행 중, 2는 복구 완료이다. 기존 최고 적용 순번, 기기 세대, 전송 큐를 보존한다. 이력 보존 기한이 이미 지나간 경우에만 기존 전체 복구 경로를 사용한다.

최신 행의 순번이 먼저 들어와 같은 테이블의 후속 행이 캐시에 반영되지 않는 경우를 막기 위해 실제 행 쓰기 횟수를 테이블별 캐시 키에 포함한다. 휴면 브라우저의 잠금이 유지돼도 유효기간과 쓰기 차단 장치가 있는 DB 임대로 안전하게 재개한다. 로그인 연결 갱신과 요청 제한 시간도 적용했다.

## 검증

- 전체 단위/DB/동기화 검증: 141개 파일, 467개 검사 통과.
- Chromium: 신규 사용성·주제 흐름 9개 검사 통과. 실제 폼 오프라인 연속 수정 검사 별도 통과.
- WebKit: 신규 사용성 및 실제 폼 오프라인 수정/새로고침 유지 5개 검사 통과.
- 두 독립 기기 저장소에서 휴대폰 메모 2개·PC 메모 1개 작성 후 양쪽 모두 3개로 동기화. 중복 없음.
- 잘못된 이전 커서를 복구해도 기기 세대와 미전송 메모 유지. 중단된 복구는 저장한 변경 페이지에서 재개.
- 프로덕션 빌드, 타입 검사, 형식 검사 통과. 빌드 추적 816개 중 비공개 파일 0개.
- 스키마 변경 027 적용 전후 활성 메모 134개로 동일. 사용자 원문과 PDF 원본을 삭제하지 않음.

실제 서비스 화면과 배포 결과는 작업 완료 시 별도 확인한다. iPhone에서는 창을 닫고 다시 열어 최신 앱 적용 후 동기화 완료·메모 3개·오프라인 저장을 확인한다.
